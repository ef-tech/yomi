# ツリー走査・描画のベンチマーク（変更前のベースライン）

Issue #83 で追加した計測の結果。**#84 が差分更新を入れる前の現行実装**の数値で、
最適化の対象範囲と改善幅を決める根拠になる。

## 再計測の手順

```bash
bun run bench                  # 1,000 / 5,000 / 10,000 で計測
bun run bench 1000 5000        # 規模を指定
rm -rf .bench                  # fixture を消す
```

fixture は `scripts/bench-fixture.ts` が生成する（`.bench/` は追跡しない）。
計測は `scripts/bench-tree.ts`。

**絶対値はマシン依存**（スキャンはファイルシステムとページキャッシュに、DOM 構築は
単一コアの JS 性能に強く依存する）。**#84 は前後を必ず同じマシンで測ること。**

### 測り方

各セルは **warmup 3 回を捨てたあと 11 回計測した「中央値（最小–最大）」**。

- **warmup を 3 回捨てる。** 1 回では足りない。DOM 構築を独立プロセスで回すと
  1 本目 ~215ms → 4 本目 ~135ms と単調に速くなり続ける（最大 61% の開き）。
  JIT が温まりきる前の値を混ぜると、中央値が定常状態より 3 割ほど高く出る
- **幅（最小–最大）も記録する。** 中央値だけだと、#84 が「178 → 160 になった」と
  言うときに**改善なのか誤差なのかを判定できない**

## 読み取れること（#84 への申し送り）

**この節は観察であって最適化の指示ではない。** #84 は実測で問題が確認できた範囲だけを
対象にするので、判断材料としてここに残す。

### 1. スキャンは `readdir` 律速ではない

10,000 ファイルで **スキャン 21.2ms のうち `readdir` は 6.6ms（約 1/3）**。
残りの ~15ms は `walk`（`src/scanner.ts`）の 1 エントリごとの JS 処理
—— `join` / `relative` / `toPosix` の文字列生成、`isExcludedPath`、`TreeNode` の
オブジェクト割り当て —— と `pruneEmpty`。

**「`readdir` の回数を減らす」というレバーは無い。** 回数は構造上ディレクトリ数
（501 回）に等しく固定されている。サーバ側で効くのは「再スキャンしない」
（キャッシュ / 差分更新）ほうであって、走査そのものの高速化ではない。

### 2. JSON 化と HTTP のオーバーヘッドは小さい

`/api/tree`（19.6ms）とスキャン（21.2ms）はほぼ同じで、差は測定の幅（±5ms）に
埋もれている。`handleTree` はリクエストごとに `scanMarkdownTree` を呼ぶだけで
キャッシュを持たないので、**応答時間はほぼスキャン時間そのもの**。

なお `/api/tree` の計測にはクライアント側のデコード（724 KB の UTF-8 パース）も
含まれており、かつサーバとクライアントが同一プロセス・同一イベントループ上にある。
実運用（別プロセスのブラウザ）とは条件が違う。

### 3. DOM 構築は jsdom 上で 177ms（実ブラウザの描画コストではない）

10,000 ファイルで 177ms。ノード数に対してほぼ線形（1,000 → 10,000 で 17.7 → 177.1）で、
ノード生成とリスナ登録の回数がそのまま効いている。

**ただしこれは jsdom の値で、レイアウトもペイントも含まない。** さらに実物は
**既定で全ディレクトリが閉じている**（`openDirs` の初期値は `[""]`）ため、501 個の
`<ul>` のうち 500 個が `display:none`。実ブラウザでは非表示サブツリーのレイアウトが
省かれるので、**実機のコスト構造は本値と一致しない**。

実機の数値が要るなら E2E（#80）側で測る。ここで分かるのは
「**DOM オブジェクトの生成回数はファイル数に線形**」までで、
「実ブラウザでどれだけ体感が改善するか」はここからは言えない。

### 4. response size は素直に増える（現状は無圧縮）

10,000 ファイルで 724 KiB。**`Content-Encoding` を付けていない**ので、この byte 数が
そのまま流れる。ローカルホストなら問題にならないが、`--share` で LAN 越しに使うなら
効いてくる。

**LAN 経由の実測はしていない**（計測は `127.0.0.1` のみ）。差分通知にするか、
その前に圧縮を入れるかは #84 が実測してから決める。

### 5. 測っていないもの

- **watcher イベント発生時の再取得時間**。ここでは初回ロードの経路しか測っていない。
  #84 が差分更新を入れるときは「1 ファイル変更 → 反映まで」を測る必要がある
- **実ブラウザでの描画時間**（上記 3）
- **メモリ使用量**。tree cache を持つなら常駐メモリが増えるので、#84 では見たほうがよい
- **除外判定のコスト**。fixture に `node_modules` などの除外対象を含めていないため、
  `isExcludedPath` は常に false を返すだけ。実プロジェクトでは `node_modules` を
  掘りかけて弾く挙動がスキャン時間に効くはずで、そこは空白のまま
- **LAN 越しの転送時間**（上記 4）
- **スクロール・TOC 生成などツリー以外の描画パス**（#83 のスコープ外）

## DOM 構築の写しについて

`scripts/bench-tree.ts` は `public/app.js` の `renderTree` / `renderNode` を**写している**
（app.js は import しただけで `init()` まで走り、ツリー描画だけを切り出せないため）。

写しは黙ってずれるので、**`tests/bench-dom-parity.test.ts` が実物と骨格を突き合わせて
固定している**。#84 が `renderNode` を書き換えたらこのテストが落ちるので、写しも合わせて直すこと。
