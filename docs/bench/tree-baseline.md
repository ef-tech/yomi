# ツリー走査・描画のベンチマーク（変更前のベースライン）

Issue #83 で追加した計測の結果。**#84 が差分更新を入れる前の現行実装**の数値で、
最適化の対象範囲と改善幅を決める根拠になる。

## 再計測の手順

```bash
bun run bench                  # 1000 / 5000 / 10000 で計測
bun run bench 1000 5000        # 規模を指定
rm -rf .bench                  # fixture を消す
```

fixture は `scripts/bench-fixture.ts` が生成する（`.bench/` は追跡しない）。
1 ディレクトリあたり 20 ファイル、10 ディレクトリごとに 1 段深くなる形で、
docs や node_modules を持つ普通のリポジトリに寄せてある。

計測は `scripts/bench-tree.ts`。各値は **5 回の中央値**（warmup 1 回を捨てたあと）。
平均だと 1 回の GC やページキャッシュミスに引きずられ、最小値だと理想状態しか見えない。

## 結果

計測環境: yomi v0.19.0 / bun 1.3.12 / Linux 6.17.0-29-generic

| ファイル数 | 実 md 数 | ディレクトリ数 | スキャン | `/api/tree` 応答 | response size | DOM 更新 |
|---|---|---|---|---|---|---|
| 1,000 | 1,000 | 50 | 1.5 ms | 1.7 ms | 68 KB | 20.3 ms |
| 5,000 | 5,000 | 250 | 8.8 ms | 9.3 ms | 358 KB | 94.4 ms |
| 10,000 | 10,000 | 500 | 20.0 ms | 20.5 ms | 724 KB | 178.1 ms |

## 読み取れること（#84 への申し送り）

**この節は観察であって最適化の指示ではない。** #84 は実測で問題が確認できた範囲だけを
対象にするので、判断材料としてここに残す。

### 1. DOM 更新が支配的

10,000 ファイルで **DOM 更新 178ms に対しスキャン 20ms**。**描画がスキャンの約 9 倍**かかっている。
ファイル数に対してほぼ線形（1,000 → 10,000 で 20ms → 178ms）で、ノード生成とイベント登録の
回数がそのまま効いている。

**差分更新の効果が最も大きいのはクライアント側**と見込まれる。1 ファイルの追加/削除で
ツリー全体を作り直すのをやめれば、この 178ms がほぼゼロになる。

### 2. スキャンと `/api/tree` 応答はほぼ同じ

`/api/tree` の応答時間（20.5ms）とスキャン時間（20.0ms）の差は 0.5ms。
**JSON 化と HTTP のオーバーヘッドは無視できる**ので、サーバ側を速くしたいなら
スキャンそのもの（`readdir` の回数）を減らすしかない。

ただし 10,000 ファイルで 20ms は、watcher イベントごとに毎回走っても
体感に出るかは微妙な水準。**サーバ側の tree cache が本当に要るかは #84 が判断する**。

### 3. response size は素直に増える

10,000 ファイルで 724 KB。ローカルホスト通信なので転送時間は問題にならないが、
**`--share` で LAN 越しに使う場合は効いてくる**（Wi-Fi 経由なら数百 ms）。
差分通知にすればここも減る。

### 4. 測っていないもの

- **watcher イベント発生時の実際の再取得時間**。ここでは初回ロードの経路しか測っていない。
  #84 が差分更新を入れるときは「1 ファイル変更 → 反映まで」を測る必要がある
- **実ブラウザでの DOM 更新時間**。jsdom で測っているので絶対値は実ブラウザと異なる。
  目的が #84 の前後比較なので、同じ条件で繰り返せることを優先した。実ブラウザの数値が
  要るなら E2E（#80）側に足す
- **メモリ使用量**。tree cache を持つなら常駐メモリが増えるので、#84 では見たほうがよい
- **スクロール・TOC 生成などツリー以外の描画パス**（#83 のスコープ外）
