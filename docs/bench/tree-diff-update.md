# ツリー差分更新の前後比較（Issue #84）

`docs/bench/tree-baseline.md`（#83）が残した**変更前**の数値と、#84 の変更を入れた
**変更後**を同じマシンで測った結果。

再計測は `bun run bench`（`rm -rf .bench` で fixture を消す）。

## 何を変えたか

1. **`changed` イベントでツリーを取り直さない。** 内容が変わっただけで構造は変わらないのに、
   `/api/tree` を取り直してツリー全体を作り直していた
2. **`tree` イベント（追加・削除）でツリー全体を作り直さない。** 同じパス・同じ種類のノードを
   再利用し、位置が合っていれば DOM を触らない
3. **`/api/tree` の応答をサーバでキャッシュする。** 構造が変わるまで使い回す
4. **再接続したらツリーを取り直す。** 1 の副作用で自動再同期の経路が無くなったため

## 結果

計測環境: bun 1.3.12 / Linux 6.17.0-29-generic / Intel Core Ultra 7 265K (20 コア) / RAM 61 GB。
各セルは **warmup 3 回を捨てたあと 11 回計測した中央値（最小–最大）**。

### watcher イベント 1 回あたりの反映コスト

`/api/tree` の取得 + ツリーへの反映。**#83 が「測っていないもの」に挙げていた区間**で、
#84 のために `bun run bench` へ足した。

| ファイル数 | 変更前 | 変更後（末尾で増減） | 変更後（先頭で増減） | 倍率 |
|---|---|---|---|---|
| 1,000 | 25.3 (22.2–27.8) | **1.4 (1.3–2.6)** | 1.5 (1.4–2.8) | 18x |
| 5,000 | 119.9 (101.5–135.2) | **9.1 (7.6–11.5)** | 8.8 (7.0–10.0) | 13x |
| 10,000 | 216.4 (205.2–238.4) | **18.2 (17.0–19.2)** | 17.8 (17.3–18.8) | **12x** |

**`changed`（内容の変更）では 0 になった。** 上表は `tree`（追加・削除）の数値で、
`changed` はツリーを取りに行かなくなったので反映コストそのものが無い
（10,000 ファイルで **216ms + 724 KiB → 0**）。

**位置による差が無い。** 素朴な差分更新だと先頭を消したときに後続の兄弟をすべて
付け替えることになる（フラットな 2,000 件で 75ms 掛かった）。消えたノードを
先に捨ててから突き合わせることで、位置によらず一定にしてある。

### `/api/tree` の応答時間

| ファイル数 | 変更前 | 変更後 |
|---|---|---|
| 1,000 | 1.7 | **0.1** |
| 5,000 | 12.3 | **0.2** |
| 10,000 | 19.6 | **0.6** |

応答の 9 割が `scanMarkdownTree` だった（10,000 ファイルで 34.7ms のうち 30.8ms。
`JSON.stringify` は 0.8ms）。構造が変わるまで直列化済みの文字列を使い回す。
常駐メモリは応答サイズぶん（10,000 ファイルで 724 KiB）。

**捨てる条件**: watcher の `rename`（外部での追加・削除）、`POST /api/file`、
`POST /api/file/create`。書き込み API でも捨てるのは、**watcher の通知が debounce のぶん
遅れる**ため —— 待つと「作ったはずのファイルが無いツリー」を返してしまう。

### 初回描画は変えていない

| ファイル数 | DOM 構築（変更前） | DOM 構築（変更後） |
|---|---|---|
| 1,000 | 17.7 (12.9–22.7) | 18.3 (16.9–30.1) |
| 5,000 | 96.9 (80.1–108.7) | 116.0 (94.3–133.9) |
| 10,000 | 177.1 (166.3–219.0) | 220.7 (195.8–251.4) |

**初回は全ノードを作るので変わらない**（差は測定の幅と、別日に取り直したぶん）。
差分更新が効くのは 2 回目以降。

## 途中で分かったこと

### ベンチが「何も変わらないとき」を測っていた

最初の `measureWatcherRefresh` は**毎回同じツリー**を流していた。差分更新なので
2 周目以降は DOM 書き込みが 0 件になり、**「変化が無いときの走査コスト」**を
「watcher イベントのコスト」として報告していた（33.1ms）。`tree` イベントの定義は
追加・削除なので、これでは測っていることにならない。

いまは**毎イテレーションで必ず 1 件足すか消す**。位置による差を見るために
末尾と先頭の 2 列に分けてある。

### 最初の差分更新は全部作り直すより遅かった

素直に書いた最初の版は **216ms → 362ms** と**悪化**した。原因は 2 つ:

1. **ノードごとに `querySelector(":scope > .tree-item")` を呼んでいた。** 10,000 回の
   セレクタ照合は、10,000 個の要素を作るより高い
2. **位置が合っているノードにも `appendChild` していた。** `appendChild` は既存ノードでも
   「取り外して付け直す」ので、全ノードぶんの DOM 操作が発生する

直した形:

- 参照（`li` / `button` / 名前の要素 / `ul`）を**作った時点で控えておく**
- `ul.firstElementChild` からカーソルを進めて、**一致していれば何もしない**
- 開閉状態も**食い違っているときだけ**書く
- **鍵の集合は必要になってから作る** —— 大半のディレクトリでは何も消えないので、
  毎回作ると 10,000 ノードぶんの Set 挿入が丸ごと無駄になる（32ms → 18ms）

**測らずに入れていたら、速くするつもりで 1.7 倍遅くしていた。**

## 残っているもの

`/api/tree` は 0.6ms まで落ちたので、残る 18ms は**クライアント側の走査**。
1 件の追加・削除でも全ノードを突き合わせている。ここを削るには**サーバが
「どこが変わったか」を通知する**必要があり、プロトコルの変更になる。
Issue #126 として切り出した。
